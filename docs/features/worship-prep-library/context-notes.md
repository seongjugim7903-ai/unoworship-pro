# 준비찬양 — 팀 레퍼토리 라이브러리 · 조 흐름

작성일 2026-08-02

## 무엇을 만드는가

1. **팀 레퍼토리 라이브러리** — 곡을 한 번 등록하면 다음 주부터는 검색해서 끌어온다
2. **조(key) 흐름 표시** — 셋 순서대로 조를 늘어놓아 인도자가 연결을 본다
3. **연주용 악보 보기** — 찬양 중에 리더·반주자가 오늘 셋의 악보를 순서대로 넘겨본다

## 악보는 준비물이 아니라 연주 중에 쓰인다

팀별로 저장해 둔 악보를 **찬양리더와 반주자가 찬양할 때 직접 본다.**
그래서 설계 기준이 "저장이 되는가"가 아니라 **"연주 중에 쓸 만한가"** 다.

여기서 따라오는 제약이 있다.

- **한 손·한 눈으로 넘어가야 한다.** 반주자는 건반에 손이 있다. 검색해서 찾아 들어가는 동선은 못 쓴다.
  오늘 셋이 순서대로 이미 펼쳐져 있어야 한다
- **전체화면·큰 화면이 기본이다.** 목록 UI 위에 작게 뜨는 미리보기로는 악보를 못 읽는다
- **예배 중 네트워크를 믿지 않는다.** 셋에 들어간 악보는 화면에 들어갈 때 미리 받아 둔다
- 페이지는 이미 모바일을 본다 (`useIsMobile`, `max-width: 600px`)

라이브러리는 이 화면에 악보를 **매주 같은 것으로** 대주기 위한 저장소다.
곡에 악보가 붙어 다니지 않으면 연주 화면이 매주 비게 된다 — 라이브러리가 먼저인 이유다.

## 하지 않기로 한 것 (2026-08-02 결정)

| 안 | 왜 접었나 |
|---|---|
| 후렴먼저·후렴만으로 슬라이드 섹션 조정 | 그 곡의 섹션을 조정해서 가져올 수 없다. 구성 값은 찬양팀이 읽는 메모로 둔다 |
| 연결(메들리) 그룹 = 한 프로그램 | 송출모드에서 이미 연결해서 볼 수 있다 |

## 프로그램 생성 방식 (결정)

```
변환본(slide-images) 있으면  →  그대로 쓴다
없으면                      →  브라우저에서 PPT 검색을 연다
```

올린 악보는 **찬양팀이 보는 용도**다. 프로그램의 원본이 아니다.
그래서 악보 파일 형태(이미지 한 장 / 여러 페이지 PDF)는 설계에 영향을 주지 않는다.

`docs/features/worship-conti/shared-ppt-search-component-note-2026-07-17.md` 의 방향과 같다.

## 왜 별도 테이블인가

"각 팀마다 사용하는 악보를 저장·**수정·삭제**" 하려면 기존 기록만으로는 안 된다.

`worship_prep_songs` 는 **회차 기록**이다. 여기서 곡을 지우면 그 주에 무엇을 불렀는지가 사라진다.
라이브러리에서 곡을 빼는 것과 이력을 지우는 것은 다른 일이므로 테이블을 나눈다.

```
worship_songs        곡 하나 = 행 하나. 악보·조·기본 구성. 수정·삭제는 여기서
worship_prep_songs   회차 기록. 그대로 둔다 (지금 동작 유지)
```

준비찬양을 저장할 때 새 제목이면 라이브러리에 자동 등록한다 — 따로 등록하는 절차를 두면 아무도 안 쓴다.

## 반주자에게 필요한데 없던 필드 3개 (2026-08-02 추가)

곡 구조 용어(Intro·Verse·Pre-Chorus·Chorus·Bridge·Interlude·Tag·Outro)를 필드로 쪼개지는 **않는다.**
슬라이드를 조정하지 않기로 한 이상 반주자는 악보를 보므로, 진행은 `직접 기입` 자유 텍스트가 더 빠르다.
필드를 늘리면 매주 채울 칸만 늘어난다.

대신 실제로 없으면 곤란한 것만 넣는다.

| 필드 | 왜 |
|---|---|
| 템포(BPM) | 없으면 매주 다른 속도로 시작한다. 반주자·드럼이 제일 먼저 보는 값 |
| 박자 | `4/4` 인지 `6/8` 인지. 6/8 곡을 4/4로 들어가면 첫 마디에서 무너진다 |
| 부르는 키 | 지금 `조(Key)` 하나로는 **악보의 키인지 실제로 부르는 키인지 모호하다.** 악보는 C인데 A로 부르는 일이 흔하다 |

전조("마지막 후렴 반음 업")는 `직접 기입` 에 적는다. 필드로 두지 않는다.

**조 흐름은 `부르는 키` 로 계산한다.** 악보 키로 계산하면 틀린 관계를 보여준다.

## 연주 화면은 아이패드·현장 기준이다

키보드 반주자가 아이패드에 받아 두고 찬양 중에 쓴다. 여기서 오는 요구가 있다.

- **화면 꺼짐 방지(Wake Lock)** — 20분 찬양 중에 화면이 잠긴다. 손이 건반에 있는데 꺼지면 그 자체로 사고다
- **발 페달** — 손을 뗄 수 없어 블루투스 페이지 터너를 쓴다. 페달은 대개 `←` `→` 또는 PageUp/Down 을 보낸다.
  넘김을 **키 이벤트로** 받아두면 페달이 그냥 된다. 나중에 붙이는 것보다 처음부터 그렇게 짜는 게 공짜다
- **셋 전체를 한 번에** 받는다. 곡마다 따로 받으면 현장에서 하나가 빠진다
- **흰 배경을 유지한다.** 어두운 예배당에서 다크모드가 오히려 안 읽힌다

## 조 흐름 — 억지로 판단하지 않는다

`song_key` 는 자유 입력이다(placeholder `예: G, Am`). 못 알아듣는 표기는 **조용히 표시하지 않는다.**
틀린 관계를 그럴듯하게 보여주는 것보다 아무 말 안 하는 편이 낫다.

관계는 다섯 가지만 본다. 그 이상은 음악적 판단이라 인도자 몫이다.

| 관계 | 예 |
|---|---|
| 같은 조 | G → G |
| 4·5도 | G → C, G → D |
| 상대조 | G → Em |
| 반음·온음 전조 | G → Ab, G → A |
| 먼 관계 | 그 외 — 표시만 하고 판단하지 않는다 |
