# 로그인 · 교회 · 팀 (features/membership)

로그인부터 교회 참여, 팀 소속, 권한까지 **이 폴더 하나에** 모여 있습니다.
바깥에는 Next.js가 요구하는 라우트 껍데기와 API만 남겨 뒀습니다.

---

## 한눈에

```
관리자 ──[담당자 링크 1:1]──▶ 담당자 ──[팀원 링크 단톡방]──▶ 팀원
```

**코드를 손으로 적는 사람은 없습니다.** 링크를 누르고 카카오로 로그인하면 끝입니다.

| 누가 | 무엇을 받나 | 누가 주나 |
|---|---|---|
| 관리자 | 교회 코드 | 구독할 때 한 번 (제품) |
| 담당자 | 담당자 링크 (1회용) | 교회 관리자 |
| 팀원 | 팀원 링크 (여러 번) | **그 팀 담당자** |

**팀원 링크는 담당자가 쥡니다.** 팀원을 부르는 것은 담당자의 일입니다 — 관리자가 모든 팀의
팀원 링크까지 나눠 주면 사람이 바뀔 때마다 관리자를 거쳐야 합니다.

**팀원 링크의 주소는 담당자가 직접 정합니다** — 카페 이름을 정하듯이. `/join/J95XAF` 는
단톡방에 붙었을 때 무엇인지 알 수 없지만 `/join/ulju-sunday1` 은 누가 봐도 우리 팀입니다.
치는 동안 중복을 확인해 주고, 이미 쓰는 주소면 만들 수 없습니다.
주소가 정해지면 **카카오톡으로 보내기** 로 공유창을 열어 대화방에 바로 보냅니다
(`NEXT_PUBLIC_KAKAO_JS_KEY` 가 없으면 버튼이 숨습니다 —
[KAKAO_SHARE.md](../../docs/features/choir-requests/KAKAO_SHARE.md)).
담당자 코드는 그대로 무작위입니다 — 1:1 로 한 번 보내고 마는 값이라 외울 일이 없습니다.

담당자로 처음 들어오면 `/my` 로 안내합니다. 그때 링크를 못 챙겼어도 거기서 다시
복사할 수 있습니다 — 1회용이 아닙니다.

권한은 **두 갈래**뿐입니다. 카테고리(설교대지·준비찬양·찬양대) 담당은 두지 않습니다 —
교회 관리자와 역할이 겹쳐 "누가 무엇을 할 수 있나"가 세 갈래가 됩니다.

| 누구 | 무엇을 |
|---|---|
| 교회 관리자 | 전부. 코드 발급, 팀 만들기, 목회자 지정 |
| 팀 담당자 | 그 팀 자료만 수정·삭제 |
| 목회자 | 설교대지를 쓴다. 남의 것은 못 고친다 |
| 그 외 참여자 | 보기만 |

## 초대 링크를 누르면 (`/join/<주소>`)

```
카톡 단톡방 링크
  → ① 앱 설치        휴대폰에서만. 끝나기 전에는 이 화면만 보인다
  → ② 카카오 로그인
  → ③ 이름 (처음만)
  → 참여 완료
```

**설치를 로그인보다 앞에 세웁니다.** 예배 중에 여는 화면이라 홈 화면에 있어야 합니다.
로그인부터 시키면 다들 브라우저에 머무르고 매번 주소를 찾아 들어오게 됩니다.
**데스크톱에서는 막지 않습니다** — 막으면 담당자가 PC로 들어올 길이 없습니다
(`lib/pwaInstall.ts` 의 `isHandheld`).

**설치하면 초대 코드를 잃습니다.** 홈 화면 아이콘은 매니페스트의 `start_url`(`/`)로 열리지
보고 있던 `/join/ulju-sunday1` 로 열리지 않습니다. 그래서 안내를 띄우는 순간 코드를
`localStorage` 에 적어 두고(`pendingInvite.ts`) 참여 화면에서 그 초대로 되돌립니다.
안드로이드는 Chrome 과 설치된 앱이 저장소를 공유해 그대로 넘어가고, iOS 는 갈릴 수
있어 안내 화면 아래에 코드를 그대로 적어 둡니다.

**설치창은 브라우저만 열 수 있습니다.** 웹이 혼자 설치할 방법은 없습니다. 대신
기회(`beforeinstallprompt`)가 오는 즉시 자동으로 띄워 보고, 브라우저가 "사용자가 직접
눌러야 한다"고 막으면 큰 버튼으로 남깁니다.

**그 기회를 놓치기 쉽습니다.** Chrome 은 이 이벤트를 페이지가 뜨자마자 한 번 쏘고 맙니다.
`useEffect` 로 리스너를 붙이면 하이드레이션 전에 지나가 버려서 **설치 버튼이 영영 안
나타납니다.** 그래서 `app/layout.tsx` 의 인라인 `<script>` 가 React 보다 먼저 받아 두고
(`window.__uljuInstall`), 화면들은 `getInstallPrompt()` 로 꺼내 씁니다.

같은 폰에서도 화면마다 결과가 갈렸던 이유가 이것입니다 — `/my` 는 다른 화면에서
이동해 들어가므로 컴포넌트가 이미 붙어 있어 이벤트를 받았고, `/join` 은 링크로 바로
열리는 첫 페이지라 놓쳤습니다.

**설치 코드는 한 곳에만 둡니다** — `lib/pwaInstall.ts` 의 `useInstall()`. 담당자 화면 위쪽
배너와 초대 첫 화면이 같은 것을 씁니다. 각자 구현해 두었더니 **배너에서는 설치가 되는데
초대 화면에서는 안 되는** 상태가 생겼고 원인을 찾는 데 오래 걸렸습니다.

**크롬은 사용자가 사이트를 좀 만져 본 뒤에야 설치 기회를 줍니다.** 링크로 막 들어온 첫
화면에서는 잠깐 없을 수 있습니다 — 그래서 기회가 없어도 버튼을 남기고, 누르면
새로고침해 다시 받습니다. 화면이 막히지 않는 것이 먼저입니다.

**자동으로 띄우지 않습니다.** 기회는 한 번 쓰면 사라집니다. 사용자가 보지도 않은 창을
실수로 닫으면 그 기회가 날아가고 화면에 누를 것이 없어집니다. 큰 버튼으로 두고 누를 때
엽니다 — 그때가 브라우저도 허락하는 시점입니다. 취소했으면 새로고침으로 다시 받습니다.

**서비스 워커가 없으면 브라우저가 설치를 제안하지 않습니다.** 등록하는 곳은
`app/pwa/PwaInstallPrompt.tsx` 입니다. 초대 화면에서는 이 배너를 화면에서만 감추고
컴포넌트는 그대로 둡니다 — 통째로 빼면 설치가 불가능해집니다.

**이미 설치한 사람에게는 설치 기회가 오지 않습니다.** 그때 "설치하세요"만 띄우면 할 수
있는 일이 없어 막힙니다. `navigator.getInstalledRelatedApps()` 로 확인해
"홈 화면 아이콘으로 여세요"로 안내를 바꿉니다 (매니페스트의 `related_applications` 가
자기 자신을 가리키는 이유).

**서버가 아파서 확인을 못 한 것과 없는 코드는 다릅니다.** 404 만 "잘못된 초대"로 보고
막습니다. 5xx 는 통과시켜 참여 단계가 다시 판단하게 둡니다 — 멀쩡한 초대를
서버 딸꾹질로 막아 버리면 안 됩니다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `inviteCode.ts` | 코드 생성·정규화, 주소 형식 검사, 권한 판정 — **순수 함수만**. 테스트는 여기를 본다 |
| `store.ts` | DB를 만지는 쪽. 코드 확인, 교회·팀 가입, 소속 조회 (서버 전용) |
| `currentUser.ts` | 지금 요청을 보낸 로그인 사용자 (없으면 `null`) |
| `requireLogin.ts` | 쓰기 라우트의 로그인 강제. `UNOWORSHIP_REQUIRE_LOGIN` 으로 켠다 |
| `AuthGate.tsx` | 입력 화면 앞의 문. 미로그인·미참여를 걸러 참여 화면으로 |
| `AuthBadge.tsx` | 홈 우측 상단. 로그인 상태와 관리자 진입점 |
| `JoinPanel.tsx` | 참여 화면 — 이름 + 교회 참여 코드 |
| `InvitePanel.tsx` | 초대 링크로 들어오는 자리 (`/join/<주소>`) — 설치 → 로그인 → 이름 순서를 세운다 |
| `InstallGate.tsx` | 그 첫 화면. 누가 어느 팀으로 부르는지 + 설치 3단계 |
| `pendingInvite.ts` | 설치를 건너 초대 코드를 넘겨주는 다리 (localStorage) |
| `LeaderHomePanel.tsx` | 담당자 화면 (`/my`) — 초대 주소 정하기(중복 검사) · 링크 복사 |
| `LeaderPanel.tsx` | 담당자 코드 직접 입력 (링크를 못 받은 경우의 보조 통로) |
| `AdminPanel.tsx` | 관리자 — 코드 발급·회수 |

**`server-only` 이 붙은 모듈은 vitest 가 읽지 못합니다.** 그래서 순수 함수를
`inviteCode.ts` 로 따로 뺐습니다. 테스트할 로직은 그쪽에 두세요.

## 판단이 갈렸던 곳

**왜 '처음 들어온 사람이 팀장'이 아닌가** — 코드는 십중팔구 단톡방에 뿌려집니다.
팀장에게 1:1로 보내도 그대로 복사해 팀원들에게 돌립니다. **팀장 자리만 1회용으로
닫아 두면** 코드가 돌아다녀도 사고가 나지 않습니다.

**주소는 되살립니다, 새로 넣지 않습니다.** `invite_codes.code` 가 전체 유니크라 회수된
주소도 자리를 계속 차지합니다. 그래서 담당자가 전에 쓰던 주소로 되돌아오면 그 행의
`revoked_at` 을 비워 되살립니다 — 안 그러면 유니크 위반으로 막힙니다.

**교회 관리자는 첫 참여자입니다.** 구독을 결제한 사람이 가장 먼저 들어오므로 위험이
거의 없습니다. 위험한 건 팀 단위뿐입니다.

**이름을 따로 받습니다.** 카톡 닉네임은 `🌸행복🌸`, `ㅁㅁ`, `아빠` 같은 것이 흔해서
관리자가 누가 누구인지 알 수 없습니다. 참여할 때 '교회에서 부르는 이름'을 한 번 받습니다.

**설교대지는 팀이 아니라 개인입니다.** 담임목사도 부교역자도 각자 자기 것을 씁니다.
`church_members.is_preacher` 로 표시합니다 — `role` 은 하나뿐이라 목회자이면서 찬양팀
담당인 경우를 담지 못합니다.

**팀 가입은 자유입니다.** 팀 경계는 '자기 팀 것만 보이게 해서 화면을 단순하게' 하는
장치이지 훔쳐보기를 막는 잠금이 아닙니다.

**카카오 동의항목을 Supabase 기본 스코프에 맞춰야 합니다.** Supabase 는 자기 기본
스코프(`account_email profile_image profile_nickname`)에 우리 것을 **덧붙입니다.**
덮어쓰지 않습니다. 그래서 코드로 `account_email` 을 뺄 수 없고, 카카오 쪽에서
프로필 사진과 이메일을 **선택 동의**로 켜야 합니다. 안 켜면 `KOE205` 로 막힙니다.

더 자세한 배경은 [docs/features/auth-church-scope/context-notes.md](../../docs/features/auth-church-scope/context-notes.md)
에 있습니다.
